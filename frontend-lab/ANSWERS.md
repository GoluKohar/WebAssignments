## Question 1: Explain CSR vs SSR vs SSG with one use case each.

### 1. CSR (Client-Side Rendering)

Client-Side Rendering is a rendering technique where the browser downloads JavaScript and renders the user interface on the client side.

- HTML produced: Initially an empty HTML shell; JavaScript renders the content.
- Typical tool: Vite SPA.
- Use case: Dashboards behind login.

### 2. SSR (Server-Side Rendering)

Server-Side Rendering is a technique where the server generates HTML for every request and sends it to the browser.

- HTML produced: Generated on each server request.
- Typical tools: Next.js and React Router framework mode.
- Use case: Personalized and SEO-friendly pages.

### 3. SSG (Static Site Generation)

Static Site Generation generates HTML pages at build time and serves them as static files.

- HTML produced: Generated once during the build process.
- Typical tools: Astro and Next.js export.
- Use case: Documentation websites and blogs.

**Conclusion:** CSR renders content in the browser, SSR renders content on the server for each request, and SSG generates pages during build time.

## Question 2: What is Hydration?

Hydration is the process in which JavaScript attaches event listeners and interactive functionality to HTML that has already been generated by the server.

It makes server-rendered or statically generated HTML interactive in the browser.

React uses `hydrateRoot` to hydrate an application.

### Hydration Mismatch

A hydration mismatch occurs when the HTML generated on the server does not match the initial HTML rendered by the client.

For example, using `Date.now()` during rendering can produce different values on the server and client.

This can cause React warnings and re-rendering.

**Conclusion:** Hydration connects server-generated HTML with React's client-side functionality to make the page interactive.

## Question 3: When is Context the wrong tool?

React Context API is useful for sharing global data such as themes and authentication information across components.

However, Context is not suitable for every type of application state.

Context is the wrong tool in the following situations:

1. **Frequent state updates:** Context may cause unnecessary re-rendering in components that consume the context.
2. **Complex state management:** Large applications with complicated state logic may benefit from dedicated state management libraries.
3. **Data fetching:** Context is not a replacement for a dedicated data-fetching or server-state library.
4. **Local component state:** If data is required by only one component, using `useState` is usually simpler.

**Conclusion:** Context is best for sharing low-frequency global data, such as theme and current user information, rather than managing every application state.
